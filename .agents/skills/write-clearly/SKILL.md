# Write clearly

Write for someone who has not read the code or followed the conversation. The reader should understand the point without asking for a second explanation.

## Start with the meaning

Lead with the answer, result, or decision. For instructions, lead with the next action. Explain what someone does and what happens before explaining how the system works. Do not force an action onto an explanation.

## Make it concrete

Use familiar words, specific verbs, and short sentences. Explain necessary technical terms where they first appear. Keep code names and file paths after the explanation.

Use one example that makes the behavior clear. For a change, show before and after. For a workflow, use current state, event, and rule when useful. Use a situation/result table when cases are easier to compare than describe.

## Keep the reading load small

Give the main point and the few details needed to understand it. Group related items and keep lists easy to scan. Preserve all requested coverage. Number sequential actions; use short paragraphs for explanations.

Do not turn a large inventory into dozens of equally prominent findings. Group related items, explain the important ones, and put the full inventory and source evidence after the explanation or in an appendix. Preserve all requested coverage. Many short entries can still make an unreadable report.

## Keep claims exact

Separate current behavior, proposed behavior, and unanswered questions. Distinguish a source reading from a tested result. Preserve useful measurements, units, conditions, and limits. Never invent evidence or present an explanatory example as an observed incident.

## Cut what does not help

Remove preambles, repeated conclusions, tangents, jargon, routine check logs, and commentary about writing the answer. State an important limit once, near the claim it limits. Use headings only when they help the reader find their place.

End when the answer is complete. If the reader must act, finish with one small, specific next action. Do not add work or a question merely to create a closing line.

Before sending, ask: Can the reader explain what happens and why it matters after one reading? If not, simplify the explanation before adding detail.
